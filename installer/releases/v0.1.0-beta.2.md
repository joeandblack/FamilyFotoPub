# Release plan: v0.1.0-beta.2 (Windows and Mac)

Status: agreed with the Windows agent in #20 (Windows side: #21 and `installer/windows/RELEASE_BETA2.md`).

**Superseded by `v0.1.0-beta.3`.** `v0.1.0-beta.2` was tagged at 689a620 and both platforms built
from it, but it was never published: the Windows release then stopped bundling FFmpeg (#26), which
changed the shared terms, so under the rule below both platforms rebuild from `v0.1.0-beta.3`. The
plan is otherwise unchanged; read `beta.2` as `beta.3` in the steps.

Goal: the first release that ships both installers, where a fresh install and a restore from a
backup work on both platforms, and every backup names exactly the FamilyFoto version to restore it
with.

## Where things stand (main at 9ae30b1)

- `v0.1.0-beta.1` is a draft release with no assets, pointing at b5e6049 (before #13 to #19).
  `pyproject.toml` still says `0.1.0b1`.
- Mac:
  - A release installation writes `restore-on-mac/RELEASE.txt` into every backup. It names that
    release's `FamilyFotoSetup.dmg` and checksum.
  - A source installation writes `restore-familyfoto-mac.command` with the exact commit it ran
    (#14). It fetches that commit and nothing else.
- Windows:
  - A release installation writes `restore-on-windows/README.txt` with that release's
    `FamilyFotoSetup.exe` link (`windows_handover`).
  - A Windows release can also name the Mac DMG for its backups (`mac_handover`, #13).
  - Gap: `restore-familyfoto-windows.ps1` (source installations) still clones the `release/0.1`
    branch, not the commit that made the backup.
- Backups move between Windows and macOS in both directions (docs/BACKUP.md).
  - Gap: a Mac release manifest has no `windows_handover`, so a backup made by a Mac release
    installation does not say which Windows setup restores it.

## The one rule that makes "the correct version" work

`setup_url` is `RELEASE_BASE/<release_id>/FamilyFotoSetup.{exe,dmg}`, and GitHub serves
`releases/download/<tag>/...`. So:

- `release_id` = the tag, exactly `v0.1.0-beta.2`, on both platforms.
- Both installers are built from the same tagged commit (`source_commit` = the tag's commit).
- Once published, assets under the tag are never replaced: backups record their links and
  checksums. A fix after publishing becomes `v0.1.0-beta.3`.

## Steps

1. **Changes before tagging (PRs to main)**
   - Windows (Windows agent): the source-install restore `.ps1` pins the exact commit, like the Mac
     launcher in #14:
     - the commit is stamped in when the backup is written, only when the code is shown to be exactly
       that commit (clean git checkout, or a verified release folder);
     - otherwise the launcher refuses before any download or administrator setup; there is no
       branch fallback;
     - it fetches only that commit, checks it out and verifies HEAD before copying. (#21)
   - Mac (Mac agent): a Mac release manifest may carry `windows_handover` {release_id, setup_url}.
     This mirrors `mac_handover`, so Mac release backups get `restore-on-windows/README.txt` too.
     The validation is the same: exactly those two keys, the official EXE link.
   - Bump `project.version` to `0.1.0b2`.
2. **Freeze.** Tag `v0.1.0-beta.2` on one main commit after those PRs merge. Push the tag; keep
   the GitHub release a draft.
3. **Build from the tag.**
   - Mac:
     - Update the build host with `brew upgrade` (the owner approves it), so the Homebrew bottles
       match current sources.
     - Collect the `sources/` folder: Homebrew source archives and formulae, and the source archives
       of copyleft wheels (the build refuses without them).
     - `build_release.py` with release_id `v0.1.0-beta.2`, the terms in `installer/legal`,
       `windows_handover` pointing at `.../v0.1.0-beta.2/FamilyFotoSetup.exe`.
   - Windows:
     - `build_shared.py` with release_id `v0.1.0-beta.2`, `mac_handover` pointing at
       `.../v0.1.0-beta.2/FamilyFotoSetup.dmg`.
     - Corresponding sources for the GPL and LGPL parts: the FFmpeg build (gyan.dev) and its
       libraries, and psycopg.
     - `installer/legal/agreement.txt` as the base terms in the Windows dialog (its `-Agreement`
       input), with the actual component notices and the model terms.
   - Each side posts its manifest digest and asset checksums in the review thread.
   - **Release-review gate for sources.** A successful build is not readiness. Before publishing,
     both agents check the source inventory by hand against what ships:
     - Mac: `build_release.py` refuses missing Homebrew and copyleft-wheel sources.
     - Windows: `build_shared.py` checks payload hashes and licence IDs only, so the FFmpeg build,
       its libraries and psycopg sources are checked in review.
4. **Qualify offline first.** Draft-release links don't work for anyone else, so test with the
   locally built DMG, EXE and payloads.
   - Mac: disposable Tart VMs.
   - Windows: a disposable full Windows VM with its own virtual disk for every library, import,
     People, backup and restore scenario. Windows Sandbox does not expose the disk identity the
     application needs (installer/windows/TEST_RESULTS.md), so it covers bootstrap and UI smoke tests
     only. A Sandbox run with skipped disk checks does not count as qualification.

   | # | Scenario | Who |
   |---|----------|-----|
   | 1 | Fresh install, without and with People | Mac, Windows |
   | 2 | Back up a release installation; check the handover files name `v0.1.0-beta.2` | Mac, Windows |
   | 3 | Restore a Mac backup on a clean Mac (QUALIFICATION scenario 8) | Mac |
   | 4 | Restore a Windows backup on a clean Windows | Windows |
   | 5 | Restore a Windows release backup on a Mac (scenario 9) | Windows makes the backup, Mac restores |
   | 6 | Restore a Mac release backup on Windows, including original-media access, People, empty People and the password | Mac makes the backup, Windows restores |
   | 7 | Restore a source-install backup: the launcher fetches the stamped commit | Mac, Windows |
   | 8 | A backup with People on but no faces restores (#17) | Mac, Windows |

   Backups for 5 and 6 are shared on a test disk image or a folder the owner names, never the live
   library.
5. **Publish as a pre-release.** Upload all assets with their exact names, publish
   `v0.1.0-beta.2` as a pre-release, then repeat scenarios 1 and 3 or 4 over the internet on each
   platform.
6. **Clean up.** Delete the empty `v0.1.0-beta.1` draft (the owner decides; it cannot be undone).
   Record results in `installer/macos/qualify/QUALIFICATION.md` and the Windows TEST_RESULTS.md.

## Agreed in review (#20)

1. Immutable tag and `release_id`, the same commit for both platforms. Windows takes the
   exact-commit launcher (#21).
2. Windows restore already accepts Mac-made backups through `app.migration.move_in`; the missing
   piece is the `windows_handover` receipt (Mac PR). Scenario 6 still has to pass.
3. The Windows build has the primitives but not yet a complete beta.2 recipe, payload and source
   bundle; the sources gate above stays.
4. Both platforms use `installer/legal/agreement.txt` as the base terms.
5. Windows owns its build and VM scenarios and provides a disposable Windows backup for scenario 5.
