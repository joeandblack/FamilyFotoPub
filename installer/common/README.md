# Shared installer implementation

This is the shared engine for the design in PR #178, with its Windows adapter
(`installer/windows/`), Mac adapter (`installer/macos/shared_adapter.py`) and Mac
launcher (`installer/macos/launcher/`); see "Mac adapter" and "Mac launcher" below.
The Mac release pipeline (payloads, release builder, audit, DMGs, qualification kit) is in
`installer/macos/` with its checklist in `installer/macos/qualify/QUALIFICATION.md`.

## Responsibilities

- `manifest.py`: pinned metadata, platform matching, dependency graph and features.
- `acquire.py`: verified cache, bounded downloads, offline-only inputs, safe ZIP extraction.
- `state.py` / `workflow.py`: explicit digest-bound acceptance, acquisition receipts,
  exclusive attempt lock, atomic checkpoints and existing `@@` progress events.
- `local_payloads.py`: local-only inputs for existing setup helpers; missing inputs
  fail instead of falling back to the network.
- `materialize.py`: shared wheelhouse/lock preparation for either platform, including
  the `password` bootstrap role.
- `stage.py`: stages the verified application release into an owned installation
  folder for either platform, recording the release link for new backups' instructions.
- `bundle.py`: offline payload assembly; completion marker written only after inputs.
- `lock_wheels.py`: release-side hash locks from resolved binary wheel directories.

Windows has a prebuilt small EXE generated by `installer/windows/build_shared.py`,
with embedded bootstrap script and pinned descriptor. It obtains private Python
and the engine before agreement, displays a combined terms/feature selection,
acquires payloads, stages application code and invokes existing Windows setup with
UAC. Existing setup owns database/restore journals and password handling. It is not
replaced by the acquisition receipt. No new service runs at bootstrap/import time.

The existing manual installers retain their behavior when no prepared payload
receipt is supplied. This permits migration without invalidating old backups.

## Release inputs

Build-time inputs must be reviewed release artifacts, not the user's running server.
Supply a recipe JSON with schema/installer version `1`, release ID, full commit,
platform `windows-x64`, agreement path and feature map. Each component has:

```json
{
  "id": "application",
  "version": "release-version",
  "url": "https://release-host.example/immutable/application.zip",
  "bundle_path": "payload/application.zip",
  "installed_size_estimate": 100000000,
  "dependencies": [],
  "license_ids": ["FamilyFoto"]
}
```

`manifest` fills actual byte sizes/hashes from the local payload tree. The example
URL is not a published release. `features.core` includes the application, Python,
both PostgreSQL primary/secondary distribution inputs, FFmpeg, password-check wheels,
core closure and People-view closure used by restored catalogs. `features.people`
adds the exact model assets only. People's provider libraries are never shipped (opencv-python and
others bundle native libraries whose sources a release cannot publish): with no provider lock in
the receipt, `pip_arguments` returns nothing for `insightface`/`facenet` and
`face_detect/cli/setup.py` installs them from PyPI by hash (Windows:
`face_detect/config/dependencies/<provider>-windows-amd64.txt`; Mac:
`installer/locks/<provider>-macos-arm64.txt`), also during an offline installation. Dependency ordering
can be expressed via component IDs. Shared artifacts should be declared once.

Application ZIPs may have application files at the ZIP root or the existing release
builder's single `FamilyFoto/` wrapper. The adapter validates and strips the latter
during extraction. Do not include databases, config/local.json,
credentials, media or backups. The release pin never follows a mutable Git branch.

Wheels retain their actual `.whl` basenames in `bundle_path`. A lock component adds
`lock_role`: `core`, `password`, `people-view`, `insightface` or `facenet`. Manifest
validation rejects unknown or duplicate roles and roles on non-`.txt` payloads.
Older manifests may contain provider locks (`insightface`, `facenet`) carrying `"wheel_index": "https://pypi.org/simple"`
and no provider wheels: opencv-python bundles a GPL FFmpeg whose sources FamilyFoto can't
publish, so setup installs them from PyPI instead, every file pinned by the lock's `--hash`. Only
those two roles may name an index, and only PyPI; materialize copies it into the receipt and
`pip_arguments` then returns `--index-url https://pypi.org/simple --require-hashes
--only-binary=:all:` for that role. Installing People therefore needs the internet, also from an
offline bundle.
A bundled native program adds `runtime_role`: `python`, `postgres` or `ffmpeg`, on a
link-free `.zip`; unknown or duplicate roles are rejected. Complete closures are
installed with no index, binary wheels only and required hashes. The checked-in
core Windows lock complements existing provider/view locks; it does not replace
their separate environments. Resolve and test every closure before publication.

Agreement input is plain UTF-8 text for the Windows reader, containing the combined
terms and required notices. It is not generated legal clearance. No placeholder
agreement or unapproved model distribution is a releasable package.

## Build commands

Run from the repository with a release-build Python, not the installed server:

```powershell
python -m installer.windows.build_shared manifest --input recipe.json --payload-root payload-tree --output installer-manifest.json
python -m installer.windows.build_shared audit --input installer-manifest.json --payload-root payload-tree --output payload-audit.json
python -m installer.windows.build_shared engine --input installer-manifest.json --payload-root payload-tree --output engine.zip
python -m installer.windows.build_shared exe --input bootstrap.json --output FamilyFotoSetup.exe
```

The build machine needs the Windows .NET Framework C# compiler; the user's PC does
not compile anything. `bootstrap.json` contains `schema_version: 1`, delivery `mode`
(`online` or `offline`), `manifest_sha256`, `bootstrap_notices`, and `python`/`engine`
objects with immutable HTTPS URL, SHA-256 and offline `bundle_path`. Python is the
official full CPython 3.12 PSF NuGet package used by the current Windows installer,
not the embeddable distribution. Its publisher signatures are checked before use.

Publish engine/payload bytes before distributing the EXE containing their pins.
EXE signing and public hosting/authentication remain release operations. This PR
does not publish binaries, embed GitHub credentials or alter public repository access.

Windows release manifests provide `minimum_os` and `setup_url`, the exact official
GitHub `/releases/download/<release_id>/FamilyFotoSetup.exe` URL. The Windows adapter
records that link with its release receipt. New backups then include
`restore-on-windows/README.txt`, with the pinned link, offline-package instructions,
`--backup` preselection and the existing restore-resume command. Old backups and
manual installations without that receipt are unchanged. No executable from the
backup is automatically trusted or run. Publishing/replacing an asset under an
existing tag is prohibited by the release process; the URL alone cannot enforce
remote immutability.
Hosting plan (owner decision, 2026-11-22): releases will be published from a fresh
public repository with GitHub immutable releases turned on; this repository stays as it
is. `RELEASE_BASE` in `manifest.py` names that public repository, `joeandblack/FamilyFotoPub`.
Before distributing a launcher, verify every release asset downloads without GitHub
credentials. The shared manifest selects EXE for Windows or DMG for Mac.

The audit verifies required Windows native payload IDs, core/view dependency locks,
both provider locks/model identities when People is offered, license-inventory IDs,
local payload sizes/hashes and agreement bytes. It emits `qualified_installation:
false`: a successful file audit is not a substitute for VM tests or legal clearance.

The headless contract, also usable by the Mac adapter, is:

```powershell
python -m installer.common plan --manifest installer-manifest.json --manifest-sha256 HASH --platform windows-x64
python -m installer.common prepare --manifest installer-manifest.json --manifest-sha256 HASH --platform windows-x64 --attempt attempt --agreement legal/agreement.txt --accept-agreement-sha256 TERMS_HASH
```

Use `--feature people` when selected. Offline preparation adds `--mode offline
--bundle PACKAGE`. It uses the same acquisition code and never downloads a missing
component. `installer.common.bundle` builds the payload tree; include the matching
bootstrap engine/runtime/EXE alongside it to make a complete offline distribution.

## Review and qualification gates

### Shared contracts for platform adapters

**Archives:** runtime ZIPs must be link-free on both platforms. Release builders
must dereference symlinks into regular-file copies, reject any source link resolving
outside their owned runtime tree, and record hashes of the resulting bytes. On
POSIX, extraction sets regular files to 0755 if any executable bit is present in
the ZIP mode, otherwise 0644. It never restores setuid/setgid or world-write bits.
Links and devices remain rejected before extraction on all platforms. Qualify the
dereferenced Python/library layout before release; do not assume every runtime
distribution works unchanged after dereferencing.

**Receipts (schema_version 1):** `stage` is the required discriminant. `prepare()`
produces `stage: acquired` with `manifest_digest`, selected `features`, component-ID
`paths`, and SHA-256 `payloads`. `materialize(manifest, receipt_path, platform,
os_version=None)` revalidates the selected inputs and atomically upgrades the same
receipt to `stage: materialized`, adding `wheelhouse` and `locks` (role -> path/hash).
Only the latter is accepted by `pip_arguments`; an acquired receipt is not enough
to provision dependencies. Both platforms use this function, not the Windows adapter.
Native install/restore journals remain independent and authoritative.

Wheel and lock materialization copies into a unique temporary file, flushes it,
and verifies its size and SHA-256 before publishing the final name. A handled
interruption or write failure removes that temporary file and leaves the acquired
receipt unchanged, so preparation can be retried. An abrupt process termination
may leave an unused `.materialize-*` file; it is never treated as a completed
payload. Existing final payloads with conflicting contents still fail closed.

**Minimum OS:** optional manifest `minimum_os` is a string of one to four numeric
components. Compare numerically with zero padding (27.0 equals 27.0.0), not as text.
Windows uses the NT version/build, e.g. `10.0.22000`; Mac uses the macOS product
version, e.g. `27.0`. `Manifest.plan()` and `prepare()` refuse older systems before
creating attempt state or downloading anything. They detect the matching host OS,
or accept an explicit `os_version` from an adapter. A different host must supply
the actual target version; it is not silently presumed compatible. Missing
`minimum_os` means no additional release-specific floor, not removal of native
adapter requirements. Mac must check this before its large runtime acquisitions.

**Events (schema_version 1):** UTF-8 `@@ {json}` lines retain the existing transport.
Every event has `schema_version`, `attempt_id`, increasing `sequence` within the
current emitter, monotonic `elapsed_ms`, `stage` and `state`. `stage` is currently
`acquire` or `prepare`; `state` is `running` or `completed`. A download count event
repeats `state: running` and includes `component_id`, `completed`, `total`, and
`unit: bytes`. `component_id` is also present on acquisition start/completion;
those events may omit counts. No count or percentage is implied when they are
absent or total is zero. `bytes` is the only current unit; readers must not guess
the meaning of future units. Attempt identity names the manifest; sequence/time
restart on a new emitter invocation. Exceptions are process failures/plain logs,
not synthetic successful completion events.

Readers must dispatch on `schema_version` **before** legacy stage/phase handling.
A v1 `acquire` event must not mark native installation done. The Mac parser needs
that explicit branch; legacy Move events without schema_version keep their current
meaning and are not converted into acquisition progress. Both windows should show
indeterminate progress for an unrecognized unit/stage, not invent a percentage.
`SetupWindow.swift` implements this in `consumeShared()`.

### Mac adapter

`installer/macos/shared_adapter.py` runs after `prepare()` as the signed-in user, never
under sudo. It materializes the receipt for `macos-arm64` (with the launcher's
`--os-version`), stages the application with `stage.py` (recording `mac_handover` and, when
the manifest names it, `windows_handover`), and
unpacks each `runtime_role` program into `<install>/bundled/<role>`. It checks every
program archive before unpacking any, and writes `bundled/<role>.json` before and after
unpacking, so an interrupted unpack is redone and a folder it does not own is refused.
After unpacking and on every resume it compares the unpacked tree with its verified
archive: every file's SHA-256 must match its archive entry, and any added file or link is
refused, except bytecode caches Python writes in `__pycache__`. That authenticates the
programs that will actually run, not just the archive. The adapter then records the
materialized receipt in `bundled/receipt.json`. `install.sh` reads it, using the bundled
Python, when `FAMILYFOTO_PAYLOAD_RECEIPT` is not set, so `bash installer/macos/install.sh
restore` resumes from a fresh shell or after a reboot without Homebrew. If the receipt or
its downloaded files are gone, it says to open FamilyFoto Setup again with the same
installation folder. The launcher should therefore keep its attempt directory in a
persistent location (for example `~/Library/Application Support/FamilyFoto`). It refuses a Mac release whose
`minimum_os` is missing or older than 27.0 (current macOS only, no legacy support) before
materializing anything.
It then runs `installer/macos/install.sh install|restore` with
`FAMILYFOTO_PAYLOAD_RECEIPT` set. The existing Mac records (`.macos-setup.json`,
`runtime/macos-*.json`, the restore journal) stay the only provisioning journal.

With that receipt the Mac installer uses only local inputs (`installer/macos/bundled.py`):
`install.sh` runs `bundled/python/bin/python3.12`; `workflow.py` takes PostgreSQL and
FFmpeg from `bundled/postgres` and `bundled/ffmpeg` and never consults Homebrew;
`prepare.py` installs the `core` closure, `setup_bootstrap.py` the `password` closure,
and People setup its provider and view closures, all with no package index. Without the
receipt every step behaves as before. Hashed Mac closures are checked in as
`installer/locks/<role>-macos-arm64.txt`. Mac releases require macOS 27 or newer by policy;
the audit also refuses any bundled program that needs a newer macOS than the release declares.

### Mac launcher

`FamilyFoto Setup.app` (`installer/macos/launcher/Launcher.swift`, built by
`installer/macos/build_launcher.py app`) is the small download. It embeds `bootstrap.json`
(the Windows descriptor schema plus `release_id` and `minimum_os`), refuses an Intel Mac,
root or an older macOS, then fetches the pinned bootstrap `python.zip` and `engine.zip`
into `~/Library/Application Support/FamilyFoto/Setup/<manifest>/`, verifying each SHA-256
(online by download, offline from the app's `Resources/bundle`, copied as bytes so a
downloaded disk image's quarantine mark is not carried over). Before unpacking it reads
each ZIP's central directory and refuses links, `..` or absolute paths and ZIP64, then
unpacks with `ditto --noqtn` into a fresh `session-<UUID>` folder, checks again for links, and
removes earlier sessions. The cache is per-user, not tamper-proof: files are re-hashed
before use, but another process running as the same user could replace a file between
that check and `ditto` reading it. The pins protect against network and storage
corruption, not against malware already running as the user.
It checks the engine's `installer-manifest.json` against the pin and the agreement against
the manifest, then shows the agreement (unchecked), the installation folder and the People
choice. Only after Install does it run `installer.macos.online_setup` with the bootstrap
Python, show its `@@` progress, and keep `attempt-<mode>` in that persistent folder so
resume works. `online_setup` refuses an occupied or linked folder and too little space
before downloading, then prepares, provisions and runs `install.sh install` with
`FAMILYFOTO_LAUNCHER=1`. With that flag `setup_bootstrap.py` opens the release's prebuilt
setup window (runtime role `setup-window`, `bin/familyfoto-setup`) instead of compiling
`SetupWindow.swift`, so users need no Command Line Tools; the window disables People when
the receipt lacks that feature. `FamilyFoto Setup --check` runs everything up to the
agreement and exits, for rehearsals.

`build_launcher.py` also builds the engine ZIP, the `setup-window` and `python-runtime`
payloads (python-build-standalone `install_only`, flattened to a link-free ZIP; links
escaping the tree are refused) and the DMG.

`build_payloads.py` makes the `postgres` and `ffmpeg` runtime ZIPs from the build Mac's
Homebrew (`postgresql@17`, `ffmpeg` — the builds deployments use). It copies the programs
and every non-system library they load into one folder, rewrites each reference to
`@loader_path`, drops outside rpaths, signs ad hoc and refuses anything still pointing
outside. PostgreSQL keeps Homebrew's relative layout (`Cellar/postgresql@17/<v>/bin`,
`share/`, `lib/`) because it finds its files relative to its own location; `bin/` holds
small launchers. `payload-info.json` records each formula's version, license files and,
only when the installed version matches the formula, its source URL and checksum.

`build_release.py` assembles a Mac release from a recipe (application, the four runtime
ZIPs, the three Core locks with their wheelhouse, both models): exact `installed_size_estimate` from
uncompressed sizes, wheels placed once, flat asset names under `RELEASE_BASE`. Its `audit`
refuses a release that lacks a runtime, lock, wheel or model; whose models are not the files
`face_detect` expects; whose sizes, bytes or agreement differ; with empty license IDs; with
`minimum_os` below 27.0; with a bundled program needing a newer macOS than `minimum_os`; or
whose native payloads lack matching sources. `bundle` audits
before building the offline bundle. `descriptor` writes the app's `bootstrap.json`, using
the bundled Python runtime as the bootstrap Python.

New backups from such an installation get `restore-on-mac/RELEASE.txt` with the
release's `FamilyFotoSetup.dmg` link beside the restore instructions, telling the user to
check the DMG's SHA-256 against the release page before the one Open Anyway approval, then
choose **Restore from a backup** in FamilyFoto Setup. A Windows release manifest may name
the Mac setup too, as `"mac_handover": {"release_id": …, "setup_url": …}` (the official
`FamilyFotoSetup.dmg` link, checked like `setup_url`); staging records it in the ownership
marker, so backups made on Windows get the same `RELEASE.txt`. Without a Mac link (a Windows
release without `mac_handover`, or a source installation), backups keep the Terminal launcher
`restore-familyfoto-mac.command`, so there is always a working way to restore on a Mac.
A bad or missing release record is logged and skipped, never failing a backup; a linked
or unexpected `RELEASE.txt` is refused like the other handover files.

The other direction works the same way. A Mac release manifest may name the Windows setup as
`"windows_handover": {"release_id": …, "setup_url": …}` (the official `FamilyFotoSetup.exe`
link). `installer/macos/build_release.py` writes it by default with the Mac release's own
`release_id`, because both platforms are published under one tag; a recipe with
`"windows": false` leaves it out for a Mac-only release. Staging records it, so backups made on
the Mac get `restore-on-windows/README.txt` naming that EXE. Without it, they get the Windows
source launcher pinned to the exact commit, or a disabled one.

### Remaining gates

The automated offline fixture rehearsal covers bundle assembly from a verified
cache, offline acquisition with network access forbidden, dependency
materialization, application staging and repeating the same preparation. Fault
tests cover interrupted and corrupted materialization followed by retry. These
tests use fixture payloads: they do not run pip, database setup, services or the
native installer, and are not substitutes for clean-machine qualification.

This branch is not a published installer release. Before marking implementation
complete and deploying it, finish these gates in this same PR:

- End-to-end clean Windows VM: new library, restore, People on/off, primary/named
  instance, interruption/resume at provisioning boundaries, no system Python/Git.
- Windows UI qualification: preparation progress and cooperative cancellation use
  the native runner/window, then hand off to the existing provisioning window.
  Closing preparation requests cancellation and waits for the worker; it does not
  kill a provisioning process or reverse a partially restored library.
- Release assembly: actual immutable hosted assets, reviewed combined agreement,
  complete notices/source materials, and tested per-platform closures/model identity.
- Qualify the new Windows handover against actual published release URLs and a
  moved backup disk. The wiring is implemented; release hosting is not yet published.
- Releases: publish each asset's SHA-256 on its release page of `joeandblack/FamilyFotoPub`,
  with GitHub immutable releases on.
- Mac signing: ad-hoc signing with one Open Anyway approval (no Apple Developer
  Program); the owner deferred Developer ID signing and notarization (2026-11-22).
- Mac: build the first release on an up-to-date build Mac (`brew upgrade`, so the audit
  finds matching sources), publish its sources, and run `installer/macos/qualify/QUALIFICATION.md`
  on a clean macOS 27 VM. Supported: Apple Silicon with macOS 27 or newer only.

Do not confuse acquisition checkpoint completion with successful installation.
The native setup's journal and verification determine provisioning completion.
Live/test servers, media, databases and backups are not used as integration fixtures.
